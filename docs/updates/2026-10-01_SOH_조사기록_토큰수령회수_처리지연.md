# 토큰 수령과 회수 처리 지연 조사

토큰 수령은 전송 후 회수 권한 승인까지 기다리고, 일괄 회수는 각 토큰의 승인과 회수를 순서대로 실행한다. 운영 감사 기록에서도 연속 단계 사이에 약 7~8초가 관찰됐다. 불필요한 승인 대기를 분리하고 회수 시 기존 승인 한도를 확인하는 방식으로 줄일 여지가 있다. 앱 변경이나 실제 토큰 거래는 이번 조사에서 수행하지 않았다.

- 조사일: 2026-10-01, Asia/Seoul.

- Frontend 기준 commit: `8a0217c4d5c6dc2bd88f1f0b2323402bd6cddfa0`, `prod`.
- 운영 ALB `soh-api-prod-alb`와 현재 ASG 인스턴스의 기존 감사 기록을 읽기 전용으로 조회했다.
- RDS managed Secret JDBC를 그대로 사용하고 연결과 SQL 트랜잭션을 읽기 전용으로 설정했다. 요청·응답 원문, 사용자 ID, 지갑 주소, 인증 정보와 개인키를 출력하지 않았다. 토큰 수령·회수 API를 실행하거나 DB를 수정하지 않았다.
- 임시 진단 프로그램과 압축 해제한 JDBC 라이브러리는 운영 인스턴스의 이번 조사 전용 `/tmp/soh-token-perf-*` 아래에 생성했다. 앱 파일·서비스 설정을 수정하거나 재시작하지 않았다.

## 운영 기록의 시간 간격

최근 7일 중 기록이 존재한 범위는 2026-09-28 10:57:56부터 2026-10-01 11:27:00까지이며 총 59개 외부 감사 기록을 확인했다. 동일 사용자의 성공한 인접 외부 호출 기록을 생성 시각과 ID 순으로 연결하고, 방문 사이의 긴 공백을 줄이기 위해 0~60초 간격만 집계했다.

| 성공 기록의 인접 단계 | 표본 수 | 최소 | 평균 | 최대 |
| --- | ---: | ---: | ---: | ---: |
| 전송 완료 → 회수 권한 승인 완료 | 8 | 5.751초 | 7.373초 | 8.219초 |
| 승인 완료 → 회수 완료 | 6 | 5.761초 | 8.137초 | 9.387초 |
| 회수 완료 → 다음 토큰 승인 완료 | 5 | 5.858초 | 7.075초 | 7.973초 |

이 값은 각 호출이 반환된 뒤 작성되는 감사 기록의 시각 차이다. HTTP 요청 시작·종료를 직접 계측한 값이 아니며 DB 감사 저장, 다음 단계 준비와 기타 처리 시간이 포함된다. 표본이 작고 사용자별 요청 상관 ID가 없어 같은 사용자의 겹치는 요청을 엄밀하게 구분할 수 없다. 전체 수령·회수의 평균이나 백분위 지연으로 해석하지 않는다.

첫 승인 대기를 약 7.1~7.4초로 가정하면, 5개 회수는 `첫 승인 + 5 × 회수 + 4 × 다음 승인`으로 약 76초, 12개 회수는 같은 방식으로 약 183초가 된다. 이는 관찰 간격을 현재 순차 코드에 적용한 예상치이며 실제 일괄 요청을 실행한 측정 결과가 아니다. 이 정도의 처리 시간이면 60초 ALB idle 한도를 넘어 화면이 먼저 실패할 수 있다. 실제 실패 원인이 ALB timeout인지 확인한 것은 아니다.

성공·실패 건수도 조회했지만 오류 응답 원문은 읽지 않았으므로 실패 이유를 추정하지 않았다. 현재 감사 테이블에는 호출 duration 필드가 없고 ALB access log도 비활성화돼 있어 과거 요청 전체의 정확한 응답 시간을 계산할 수 없다.

## 개선 우선순위

1. 수령 응답의 전송 완료와 회수 권한 승인 처리를 분리한다. 승인을 회수 시점으로 옮기거나 내구성 있는 후속 작업으로 처리하면, 수령 중 현재 승인 대기를 줄일 수 있다. 실제 전송이 확인된 뒤에만 수령 완료로 표시하며 승인 실패와 재시도는 보존해야 한다.
2. 회수 시 holder·contract·spender의 실제 allowance를 확인하고 충분하면 재승인 트랜잭션을 생략한다. 부족하거나 조회가 실패하면 기존 승인 절차를 유지한다. 지갑 초기화와 owner·contract 변경, 승인 성공 이후 전파 시간도 검증한다. 현재 회수 시 승인 보호를 단순히 제거하지 않는다.
3. 일괄 회수는 작업 ID와 처리 상태 조회를 제공하는 지속 가능한 작업으로 분리한다. 서버는 토큰별 실제 성공을 저장하고 화면은 진행 상태를 표시한다. 60초 요청 하나에 모든 거래를 묶는 문제를 줄이면서 실패·부분 성공·재시도의 중복 방지를 유지할 수 있다.
4. 외부 호출과 수령·회수 전체에 소요 시간 및 작업 상관 ID를 기록한다. endpoint와 상태, duration만 기록하고 비밀값은 제외한다. 실제 전송 지연과 승인 지연, DB·UI 대기를 구분한 뒤 변경 전후를 비교한다.

무조건 병렬화하는 방안은 권장하지 않는다. 같은 지갑과 운영 owner의 여러 chain 거래를 동시에 보내도 되는지, 외부 서버 제한과 순서 의존성, 중복 지급·회수 및 부분 성공 보호를 별도로 검증해야 한다. timeout을 짧게 바꾸는 것만으로 거래 처리 속도가 빨라지지 않으며, 화면이 실패한 뒤 외부 거래만 성공하는 상태를 처리할 설계가 필요하다.

## 검증과 배포 영향

- 관련 backend·frontend 코드, prod의 12개 contract 설정과 운영 ALB 속성을 확인했다.
- 운영 감사 기록 SQL은 읽기 전용 트랜잭션 안에서 실행 후 rollback했다. 실제 전송·회수·승인 거래는 발생시키지 않았다.
- 조사 문서에 `git diff --check`를 수행한다. 앱 코드·API·DB schema·Secret·배포 설정은 변경하지 않아 앱 build/test는 생략한다.
- 이 기록만 `[skip ci]`로 commit/push한다. 새 앱 배포나 ASG refresh는 요청하지 않는다. 다른 로컬 변경은 포함하지 않는다.
- 복구가 필요한 앱·DB 변경은 없다. 문서 rollback은 해당 조사 기록 커밋을 revert하면 된다.
