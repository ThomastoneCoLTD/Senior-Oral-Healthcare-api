## 코드와 오류 해석

- `ExternalTokenClient.post`: 외부 `state=OOPS`를 지급 실패로 판단하고 외부 응답을 실패 감사로 저장한 뒤 `BadRequestApiException`을 던진다.
- `UserRewardService.transferTokenIfConfigured`: 실패 상태를 거래에 저장하고 원인을 포함한 지급 오류를 전달한다. 이번 건은 전송 단계에서 실패하여 이후 해당 contract의 승인 단계에 도달하지 않았다.
- `OralExerciseController.rewardButtonClick`: 정답 번호가 일치하는 서버 요청 실패를 별도 `TOKEN_FAILED`로 기록한다. 실제 오류 감사에서도 선택 번호와 정답이 모두 1이다.
- 정답 선택 시간 초과(`TOKEN_TIMEOUT`)와 이번 서버 지급 실패(`TOKEN_FAILED`)는 별개다. 직전 영상의 성공 기록은 지갑 발급·활성화가 완료됐다는 보조 증거이며 모든 contract의 정상 상태를 보장하지는 않는다.
- `read response head / read data type`와 `Application error 0x0 (local)`는 외부 Mitum 응답을 읽던 연결이 애플리케이션 오류로 종료됐다는 해석과 부합한다. [quic-go 공식 연결 문서](https://quic-go.net/docs/quic/connection/)는 `ApplicationError`와 handshake/idle timeout을 구분한다. 이번 오류를 명시적인 timeout, 잔액 부족, 서명 오류, 사용자 오답으로 확정할 근거는 없다.
- `(local)`은 외부 오류를 생성한 통신 구성요소 기준이며 사용자의 PC나 SOH 프론트엔드를 뜻하지 않는다. 연결 재사용 문제, 외부 서비스 재시작, 내부 취소 등 구체적인 종료 원인은 외부 토큰 서버와 Mitum 노드의 같은 시각 로그가 필요하다.
- 현재 수령 경로 `transferTokenToWallet`에는 자동 재시도가 없으므로 외부 오류 한 번으로 지급 실패가 유지된다. 기존 수령 요청 재실행 시 실패 거래를 재사용하는 로직은 있으나, 외부 체인 반영 여부를 먼저 확인해야 중복 지급 위험을 줄일 수 있다.
