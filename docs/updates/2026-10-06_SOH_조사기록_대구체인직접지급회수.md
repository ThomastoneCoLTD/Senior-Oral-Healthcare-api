# 대구체인 직접 지급과 회수 소스 조사

사용자 요청은 운영 변경 없이 직접 연결 가능성을 확인하는 것입니다. 로컬 가입의 DID 발급은 SOH_DID 서버에 유지합니다. 거래 요청, 운영 설정, 지갑·회원 데이터, 토큰 전송 코드는 변경하지 않았습니다.

## 기준과 확인 범위

- SOH API 기준: `ce25e21f`, 로컬 `prod`. 메일 비활성화 변경은 이 조사와 별도로 진행했습니다.
- SOH_DID 기준: `hanathomastone/SOH_DID`의 `8e7c443b66f8d7bd13fd06c59993c93b8a9b3391` 소스를 임시 복제해 정적 분석했습니다. 실행하거나 설정값을 가져와 적용하지 않았습니다.
- 운영 서버의 실제 배포 커밋, 유효 환경변수, 인증 권한, 실제 전송 결과는 이번 조사에서 확인하지 않았습니다. 소스상 구현 가능성과 운영 동작 검증을 구분합니다.

## 결론

| 기능 | 현재 코드 | 직접 연결 판단 |
|---|---|---|
| 로컬 DID | SOH → SOH_DID `/did/create` | 사용자 조건대로 유지 |
| 보상 지갑 | SOH → 대구체인 `/mitum/com/acc_create`, `/mitum/com/acc_faucet` | 이미 직접 생성·활성화하고 암호화된 키를 SOH DB에 저장 |
| 잔액과 거래 확인 | SOH → 대구체인 balance·transaction API | 직접 호출 구현 존재. 잔액만으로 지급 완료를 확정하지 않음 |
| 기존 토큰 지급 | SOH → SOH_DID `/token/transfer` → 대구체인 `/token/transfer` | 직접 `transfer`로 대체할 수 있는 구조. 기존 토큰 이동이며 create·mint를 호출할 필요 없음 |
| 현재 보상 지갑 회수 | SOH에서 직접 approve 후 SOH_DID `/token/retrieve` → 대구체인 `/token/transfer_from` | SOH가 사용자 지갑 키를 가진 경우 직접 `transfer_from`으로 대체할 수 있는 구조 |
| 이전 지갑 회수 | SOH_DID에서 저장한 지갑 키를 찾아 approve 후 transfer_from | 키가 SOH_DID에만 있으면 중계 경로를 유지하거나 별도 승인·이관이 필요 |

## 지급과 회수의 중계 역할

SOH_DID `main/myapp/routes/token.py:179`는 수신한 지급 요청에 관리자 주소와 키를 보충한 뒤 대구체인 transfer로 전달합니다. `user_DID`가 있으면 중계 DB의 지갑 주소로 receiver를 바꾸고 자체 잔액 기록도 갱신합니다. 현재 SOH 리워드 지급은 `transferTokenToWallet`로 실제 보상 지갑 주소를 보내며 `user_DID`를 보내지 않으므로 이 DID 조회와 자체 잔액 갱신 분기는 실행되지 않습니다. 설정된 계약 주소를 우선 사용하고 누락된 경우 토큰 목록 중계 조회가 남아 있습니다.

SOH_DID `routes/token.py:237`의 retrieve는 sender·receiver·관리자 키가 서버 설정과 일치하는지 확인합니다. 이전 지갑 키를 서버 파일에서 찾을 수 있으면 사용자 지갑의 approve를 추가 수행하고 transfer_from으로 전달합니다. SOH 자체의 현재 보상 지갑은 `UserRewardWallet`에 암호화된 키를 저장하고 SOH에서 직접 approve하므로 이 키 조회가 필요하지 않습니다. 회원 삭제·초기화는 이전 지갑의 중계 키 조회에 의존할 수 있어 일괄 우회하면 안 됩니다.

SOH의 `DaeguChainClient`와 `DaeguChainToken20Service`에는 `/mitum/token/transfer`, `/mitum/token/transfer_from` 직접 호출이 이미 있습니다. 그러나 리워드 지급 흐름에 그대로 연결하기 전에는 업무 오류 상태, 거래 제출 여부, fact_hash·receipt·수신 지갑·계약·수량 확인을 기존 `RewardTransferRecoveryService` 및 `RewardTransferReceipt` 계약에 맞춰야 합니다. 전송 API의 OK 응답이나 잔액만으로 완료 판정을 바꾸지 않습니다.

## DID만 중간 서버에서 받는 경우

SOH의 `UserDaeguProvisioningService`는 중간 서버 응답에서 DID를 저장한 후 `DaeguRewardWalletProvisioningService.createActivatedWallet`을 따로 호출합니다. 신규 로컬 가입의 보상 지갑은 이미 대구체인 직접 발급 주소입니다. SOH_DID 응답의 주소를 보상 지갑으로 재사용하지 않습니다.

다만 SOH_DID의 현재 `/did/create`는 `routes/did.py:401`에서 대구체인 지갑도 필수로 생성한 뒤 DID와 함께 저장합니다. 지갑 생성 실패 시 DID 응답 자체도 실패합니다. 따라서 현재 흐름은 중간 서버에서 사용하지 않는 별도 지갑이 추가 생성될 수 있습니다. DID만 발급하는 요청 옵션이나 API는 현재 이 코드에 없습니다.

DID만 발급하도록 분리하려면 향후 SOH_DID에 선택적 DID 전용 모드를 추가하는 방안을 검토할 수 있습니다. 기존 기본 동작은 유지하고 SOH의 신규 요청에만 적용하며, DID 문서·키 보관과 MySQL 저장이 지갑 없이도 동작하도록 함께 검증해야 합니다. 옵션 이름·계약은 아직 구현하거나 확정하지 않았습니다. 기존 DID와 지갑은 변경·삭제하지 않습니다.

## 운영 영향을 줄이는 전환안

1. 우선 DID 발급과 현재 지갑 생성·활성화 흐름을 유지합니다. 기존 지갑 재생성이나 잔액 이관은 수행하지 않습니다.
2. 지급과 회수의 직접 호출을 각각 선택할 수 있는 서버 설정을 설계하며 초기값은 기존 중계 방식으로 둡니다. 검증된 현재 보상 지갑만 대상으로 단계 적용합니다.
3. 중계 서버와 SOH가 사용하는 API base/version, chain ID, 호출용 user token, 관리자 주소·서명 키, 기존 토큰 계약을 대조합니다. 소스 기본 chain ID는 SOH `dchain`, SOH_DID `minic`으로 다르므로 운영값이 같다고 추정하지 않습니다. 실제 키 값은 출력·기록하지 않습니다.
4. direct 모드에서도 현재 비동기 처리, DB 잠금, 중복 방지, 거래 증명 확인, 확인 중 지급의 회수·삭제 차단을 유지합니다. 타임아웃 후 proxy 모드로 즉시 재전송하는 fallback은 금지합니다. 먼저 기존 거래를 확인합니다.
5. 이전 지갑의 회수는 중계 경로를 남깁니다. 지급·회수 오류만으로 지갑을 교체하거나 기존 지급을 재실행하지 않습니다.
6. 추후 승인된 시험 환경에서 동일 토큰 계약과 현재 지갑을 대상으로 확인한 뒤 제한적으로 전환합니다. 이번 조사에서는 실제 거래를 수행하지 않았습니다.

중계 서버를 우회하면 해당 토큰 경로의 중간 HTTP 구간은 제거할 수 있습니다. 대구체인 공식 API가 요구하는 개인키 전달은 남으므로, 이 전환만으로 개인키 미전달 서명 구조까지 해결한 것으로 판단하지 않습니다. 원청 API의 승인 거부도 중계 제거만으로 해결된다고 보장하지 않습니다.
